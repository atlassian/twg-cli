# Workflow-first space blueprints

Use these as hypotheses, not templates. Shape branches from evidence and named
workflows; give every retained hub a `page-archetypes.md` recipe.

`Home` below means the auto-created space homepage. Update that content item;
do not create a second root home.

## Scale choices

- **Lean-rich** — substantive hubs plus only workflow-critical companions;
  default for ambiguous briefs.
- **Standard** — evidenced functions, maintained templates, and trackers.
- **Expanded** — multiple teams, services, or workstreams; requires counts,
  stages, a representative vertical slice, and approval before expansion.

These are not quotas. Explain the evidence behind every large branch.

## Product or initiative space

Recommended lean-rich shape:

- Home
- Product Strategy
- Roadmap and Delivery
- Customer and Research
- Architecture
- Decisions _(folder)_
- Launches and Learning

When justified, add Metrics, Experience Design, Operations, Security and Trust,
Ways of Working, or Reference. Prefer maintained trackers/maps over empty leaves.

For a brief-only source, create a rich scaffold from known context without
inventing owners, dates, metrics, evidence, decisions, or runtime facts.

## Team space

Recommended lean-rich shape:

- Home
- Mission and Ownership
- Goals and Priorities
- Ways of Working
- Projects _(folder)_
- Decisions _(folder)_
- Onboarding

Add catalogs, maps, rituals, or updates only with a maintainer. Link canonical
work trackers instead of copying backlogs.

## General-purpose space

Recommended lean-rich shape:

- Home
- Purpose and Outcomes
- Workstreams _(folder)_
- People and Participation
- Knowledge and Resources
- Decisions _(folder)_
- Updates and Learning

Use this only when other shapes do not fit. Rename, replace, or remove every hub
from evidence; different user jobs should produce different spaces.

## Repository-informed space

A repository is evidence, not a space category. Start from purpose and the
closest workflow shape, then load `repo-discovery.md`. Retain only branches
needed by the actual audiences; code does not imply an engineering taxonomy.

## Existing-space adaptation

Default to structure adaptation rather than body copying:

1. Read the tree to depth three, available instructions, and a bounded sample.
2. Identify workflow, navigation, naming, lifecycle, voice, content placement,
   and stale or source-specific branches.
3. Propose what to preserve, adapt, collapse, or omit and each body relationship.
4. Copy bodies only when approved; never imply-copy access or public links.

Do not claim a “style clone” without body samples or crawl the whole source just
to propose structure.

## Page, folder, and hierarchy rules

- Use folders only for navigation and pages for explanatory nodes.
- Replace a folder that needs orientation with a hub, or add a purposeful child.
- Prefer recognizable workflow hubs over flat lists or deep taxonomies.
- Put narrow reference under its workflow or a bounded Reference folder.
- Every page needs a user job, recipe, source/body mode, and maintenance plan.

## Source-to-body policy

Use the grounded/adapted/scaffold/mirror modes defined in `proposal-flow.md`.
For repository evidence, choose synthesis, import, attachment, or canonical link
per artifact; volatile or generated material usually remains a link.
