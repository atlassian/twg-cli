# Page archetypes and rich composition

Load while turning a blueprint into the composition map. This decides **what
belongs together**; live `body-formats` guidance decides exact syntax.

## Select content by job

- **Page/live doc** — explain, orient, decide, teach, or synthesize.
- **Folder** — group navigation with no narrative job.
- **Database** — repeatedly add, filter, assign, or review records with a stable
  schema.
- **Whiteboard** — understand flows, journeys, dependencies, clusters, or
  workshop input spatially.
- **Smart link/embed** — keep an external system canonical in context.
- **Attachment** — preserve a bounded artifact whose fidelity matters.

A database or whiteboard normally has an owning page for purpose, scope,
maintenance, and interpretation. Skip it when a page section or table suffices.

## Composition recipes

### Home / Start Here

Route each audience's next action with purpose, ownership, current state,
workflow navigation, canonical links, and contribution guidance. Avoid a
decorative whiteboard or sidebar copy.

### Product strategy / initiative

Cover problem, thesis, outcomes, measures, principles, non-goals, constraints,
dependencies, questions, and decisions. Add a database for recurring
prioritization or a whiteboard for spatial relationships/sequencing.

### Roadmap / delivery

Keep horizon, themes, decision/status rules, and maintenance on the hub. Use a
database for recurring initiatives and a whiteboard for dependency planning,
never as the sole truth. Link Jira rather than copying issue-level tracking.

### Architecture / system context

Explain scope, boundaries, responsibilities, components, interfaces, data flow,
trust, constraints, failure modes, observability, decisions, and runbooks. Add
a system/data-flow whiteboard for spatial relationships and a maintained catalog
for many components; keep the page as entry point.

### Research / insight

Record question, method, source/participant boundaries, findings, confidence,
implications, limitations, and evidence. Use a database for recurring evidence
and a whiteboard for spatial synthesis. Never invent quotes or findings.

### Decision / RFC / ADR

Include status, context, owner, options/trade-offs, outcome, consequences,
follow-ups, and supersession. Use an index database for many decisions and a
whiteboard only when it materially informs a record readable without it.

### Runbook / operations

Include owner/escalation, symptoms, impact, prerequisites, safe diagnostics,
recovery, verification, rollback, observability links, and risks. Add a service
catalog, incident/problem tracker, architecture map, dashboards, or automation
links only when maintained. Never copy secrets or unverified commands.

### Team / ways of working

Show mission, boundaries, roles, contact paths, collaboration expectations,
rituals, decision model, goals, and onboarding. Link canonical people and work
systems. Add an ownership catalog for a large domain or a working-agreement
whiteboard for an active workshop, not as decoration.

### Launch / release

Coordinate scope, audience, success and guardrail measures, milestones,
dependencies, readiness, rollout/rollback, communication, support, owners, and
learning. Use a readiness/milestone database, launch-dependency whiteboard,
or canonical Jira plan when the workflow recurs. Keep announcement publishing
outside this workflow. Distinguish planned, confirmed, and unknown.

### Reference / glossary / catalog

State scope, ownership, update policy, and concise definitions or fields. Use a
database when readers filter a stable schema; use a table or child pages for a
small narrative set; prefer smart links for externally owned catalogs.
Whiteboards are rarely useful.

### Meeting / workshop

Include purpose, participants, pre-reading, agenda, notes, decisions, and owned
actions. Add a whiteboard for mapping, clustering, voting, or co-design. Move
durable decisions into their canonical area rather than leaving them only in
meeting notes.

## Quality gate

A rich scaffold may contain meaningful prompts, starter tables, status/owner
placeholders, canonical links, and repeatable templates without fabricating
facts. Remove any artifact that cannot answer:

1. What user job and audience does it serve?
2. Who maintains it, and what is canonical?
3. Why is this type better than a section on an existing page?
4. What narrative page owns it, or why is none needed?
5. Is its body grounded, adapted, scaffolded, or explicitly mirrored?
